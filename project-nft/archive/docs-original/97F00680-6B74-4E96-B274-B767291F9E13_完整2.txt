## 四、API 调用分析

### 4.1 请求封装

**文件**: `/workspace/shuheWC/frontend/src/api/request.js`

- **基础配置**: `baseURL: '/api'`, `timeout: 15000`
- **请求拦截器**: 从 localStorage 读取 token，添加 `Authorization: Bearer {token}` 请求头
- **响应拦截器**: 
  - 成功：直接返回 `response.data`（后端统一格式 `{ code, data, message }`）
  - 401 错误：自动刷新 token（`POST /api/user/refresh-token`），支持并发请求队列排队，刷新失败则清除本地数据并跳转登录页
  - 其他错误：`showToast(message)` 显示错误提示

### 四、提示词存在的问题和需要修正的地方

#### 4.1 库存模型语义冲突（必须修正）

提示词 4.1.1 定义：

> 库存池（自由库存） = 发行总量 - 已配置配额 - 已售出发售 - 已独立空投 - 已销毁

现有数据库 `nft_collectibles` 中 `circulate` 字段语义是「可售数量」，并非提示词中的「流通量」（已进入用户仓库的数量）。提示词需要明确：

- 现有 `circulate` 字段应重命名或重新定义语义为「库存池/自由库存」
- 需新增 `in_circulation` 字段表示「流通量」（= sold + airdropped_count）
- 或者保留 `circulate` 原义但新增 `free_stock` 字段

#### 4.2 资格购 vs 优先购概念混淆（需要厘清）

提示词 4.2 定义了一种新的「资格购」机制（持有特定藏品才能购买），这与现有的「优先购」（`nft_priority_sales`）是**完全不同的功能**：

- **优先购**（已有）：白名单用户在特定时间窗口内优先购买
- **资格购**（提示词新增）：用户必须持有指定藏品才能购买

提示词需要明确说明这两者的关系，并要求后端新建 `nft_eligibility_purchases` 表。

#### 4.3 盲盒表结构差距过大（需要重建）

现有 `nft_blind_boxes` 仅有 5 个字段（id, collectible_id, is_delete, created_at, updated_at），提示词要求盲盒有独立的发行总量、库存池、流通量、发售配置、状态流转等。这本质上需要**重建盲盒表**。

#### 4.4 奖励类型统一需要 ENUM 扩展（需要明确）

提示词 4.7 要求全平台奖励类型统一为：藏品/优先购白名单资格/资格购资格/抽奖次数/盲盒。

现有各表的奖励相关 ENUM：
- `nft_check_in_records.reward_type`: `('none','collectible','points','draw_chance')` — 缺少 `priority_qualification`、`eligibility_qualification`、`blindbox`
- `nft_lucky_draw_prizes` 无 `prize_type` 字段，仅关联 `collectible_id`

提示词需要明确列出所有需要扩展的 ENUM 字段。

#### 4.5 订单 source 需要扩展（需要明确）

现有 `nft_orders.source` ENUM 仅 `('release','market')`，提示词 8.6 提到「公售/优先购/市场购买/资格购/盲盒购买」5 种类型。需要扩展为：

```sql
ALTER TABLE nft_orders MODIFY COLUMN source ENUM('release','market','priority','eligibility','blindbox') NOT NULL;
```

#### 4.6 角色数量不匹配

现有 `nft_admin_users.role` 注释为 4 种（1=超管 2=运营 3=财务 4=客服），提示词要求 5 种（超管/运营/财务/风控/客服）。需新增 `role=5`（风控）。

#### 4.7 提示词缺少与现有 C 端后端的集成说明

提示词未说明管理后台后端与现有 C 端后端的关系：
- 是同一个 NestJS 项目新增 Admin Module？
- 还是独立的新项目共享同一个数据库？
- Admin JWT 与 C 端 JWT 是否隔离？

建议提示词增加「后端架构要求」章节。
